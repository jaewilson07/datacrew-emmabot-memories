# Environment / Tooling Gotchas

- **Bash tool requires bwrap (bubblewrap)** — the Letta Code CLI uses it for command sandboxing. Error `Executable not found: /usr/bin/bwrap` means bubblewrap isn't installed. Fix: `sudo apt-get install bubblewrap` (Debian/Ubuntu). When Bash is broken: can't clone repos, run commands, dispatch Claude Code/Codex, or use skills that require Bash. This occurs on local machines without bubblewrap; Docker containers typically have it.
- **MCP server URL is `wiki.datacrew.space` not `mdrag` or `wikki`** — old `mdrag.datacrew.space` 301-redirects to `wiki.datacrew.space` (one 'k'). `wikki.datacrew.space` (two k's) also redirects. Always use `https://wiki.datacrew.space/mcp/` directly.
- **`wikki.datacrew.space` 301 is an ERROR for httpx clients with `follow_redirects=False`** — `https://wikki.datacrew.space/*` 301-redirects to `https://wiki.datacrew.space/*`, and clients like pattern-hunter's MdragFeedClient treat the redirect as a failure (`FeedUnavailableError: "mdrag feed answered 301"`). Always configure MDRAG_URL with the canonical `wiki.datacrew.space` host (pattern-hunter deploy #10 must use the wiki host in Infisical).
- **`save_url_to_knowledge` returns 401** — internal auth forwarding bug on the wiki MCP server. Use `save_text_to_knowledge` instead — read the content locally and pass as text.
- **MCP toolsets are lazy-loaded** — call `list_capabilities` to see all toolsets, then `reveal_toolset(name)` to access tools. Default tools don't include `search_web`, `query_rag`, etc. — they're in the `web` and `rag` toolsets.
- **MCP requires SSE Accept header** — must send `Accept: application/json, text/event-stream` or get "Not Acceptable" error. Responses come as SSE events (`event: message\ndata: {...}`).
- **MCP session ID required** — after `initialize`, extract `Mcp-Session-Id` from response headers and include it in all subsequent requests.
- **Never `env | grep` without filtering** — printing all env vars exposes secrets (Slack tokens, API keys, JWTs, OAuth credentials). Always filter to specific vars or use `grep -i VARNAME` for a single var.
- **Mods at `~/.letta/mods/` run on ALL agents** — bonker hosts EmmaBot, IdrisBot, and DataCrew; a harness-level mod affects every agent. Agent-specific mods must go in `$MEMORY_DIR/mods/` (agent-level). The dug-community mod was originally at harness level and caused all 3 agents to trigger simultaneously on the same doc gaps.
- **dug-community state is harness-scoped** — `~/.letta/mods/dug-community-state.json` is shared by all agents. If one agent resolves a gap, the others see it. If one resolves with a wrong `resolutionPath`, the others inherit that error. Always verify another agent's resolution path points to a real file.
- **mdrag ingestion requires `uv` + `httpx`** — the ingestion function uses `uv run --with httpx python3 -c "..."` (not the crew-dcs package, which may not be installed). Requires the `domo-official-docs` collection to pre-exist on mdrag. If `domo-rag.ts` `queryMdrag` fails: it uses `source_group` parameter — the correct param is `topics`. Also needs `reveal_toolset("rag")` called before `query_rag`, and must NOT depend on `/tmp/crew-dcs` directory (use `uv run --with httpx` from any directory).
- **Embedding-gateway outage fallbacks** (learned 2026-09-11, mdrag#1573): when `domo_rag_query` 502s (cubby's llama-swap gateway down), these still work — `GET /api/v1/documents?q=` (Mongo full-text, doc titles not chunks), `POST /api/v1/search` (unified), `POST /api/v1/searxng/search` (mdrag's web search — no embeddings needed; use as research fallback BEFORE letta's web_search, it found the authoritative Salesforce help doc for the formula-field question), and `POST /api/v1/ingest/annotation`. Broken during outage: `POST /api/v1/query` (500s even with `search_type: "text"` — that's the bug).
- **Mod file management** — I maintain my own mods (Jae 2026-09-11): edit at runtime (`~/.letta/mods/`), then `bash ~/GitHub/infra-bonker/apps/letta-code-channels-datacrew-public/sync-mods.sh` to reconcile with the repo (two-way, newest mtime wins; Claude may write mods into the repo — sync pulls them to runtime). The sync also runs automatically on every service start via `start-bare.sh`, auto-commits synced changes, and never syncs secrets/state (`.domo_rag_config.json`, `dug-community-state.json`, `diagnostics/`). A service restart (`systemctl --user restart letta-datacrew`) is still required for mod changes to take effect — mods are not hot-loaded.
- **NEVER restart letta-datacrew.service from a Bash tool call** — I run *as* that service; restarting kills my own process mid-tool-call, the call never returns, and the harness reports a client/server state desync (re-issuing just dies again). Schedule it detached instead: `nohup bash -c 'sleep 45 && systemctl --user restart letta-datacrew.service' & disown` so it fires after the turn ends. Then verify with a Monitor or a later Bash call (`systemctl --user is-active`).
- **`node --check` passing ≠ TS file valid** — `node --experimental-strip-types --check` passes on files with unbalanced braces (its parser error-recovers); `npx tsc --noEmit` and `npx tsx` both catch what it misses. To test a mod end-to-end without restarting the service: `npx tsx /tmp/test.mts` importing the mod with a stub `letta` object (`tools.register` collecting tools, then call `tool.run({args, cwd, agent, conversation})`). The mdrag-annotation mod shipped for days with a missing `}` closing the `tools.register` object — it only loaded because the runtime's parser error-recovered (2026-09-18).

- **Web search name collisions** — searching for "Domo" + "tour" returns music tours (DOMi & JD Beck, a jazz duo with a 25-city fall 2026 tour) instead of the Domo Connections Tour. Use `site:domo.com` or `"Domo Connections" "AI Data Tour"` to disambiguate. This pattern applies broadly: any company name that could overlap with entertainment/brand names will pollute search results.
- **JS-rendered pages return minimal HTML** — Domo events pages (main tour page, events hub) are JS-rendered. `curl`/`fetch` returns empty agenda/location sections. JSON-LD structured data may be present but often contains stale data. Prefer scraping individual city pages on the webflow subdomain (`domo-webflow.domo.com`) which have richer metadata.

- **`resolve_doc_gap` auto-ingest misses PR-branch docs** (confirmed 2026-10-09) — it ingests the resolution doc into mdrag by reading it from the filesystem path, but all doc work now goes through GitHub PRs (Jae's directive), so the doc typically exists only on the PR branch, not in the working tree on main. Result: `mdrag ingestion: skipped (file not found at .../knowledge-base/domo/gotchas/<doc>.md)`. Workaround: extract the doc from the branch (`git show <branch>:reference/domo/gotchas/<doc>.md`) and ingest manually via `POST http://localhost:8017/api/v1/ingest/text` with `DATACREW_API_TOKEN`, fields `content`/`title`/`collection`. Notes: the ingested copy lands in collection `personal:jaewilson07@gmail.com` (not `domo`) and its title renders with a provider_type quirk, but it's annotatable and content-searchable; the canonical copy replaces it after the PR merges.
- **`capture_domo_doc_learning` quotation must be verbatim in the SUBJECT doc** (confirmed 2026-10-09) — the underlying annotation endpoint enforces that `quotation` is a verbatim substring of the subject document; a quote that appears only in the Slack thread is rejected with HTTP 422 `citation_quote_not_found`. Use a quote that appears verbatim in BOTH the thread and the subject doc.
- **`pkill` matches its own wrapping shell** — when `pkill <pattern>` is run inside a compound Bash command where the pattern string appears in the command itself (e.g., `pkill uvicorn; nohup uvicorn ... &`), `pkill` can match and kill the wrapping shell process, terminating the entire compound command before subsequent commands (`nohup ...`) can start. Fix: use a more specific pattern like `pkill -f "uvicorn --port 8765"` with unique flags, or use `fuser -k <port>/tcp` to kill by port instead. Alternative: `kill $(lsof -ti:8765)` to target specific PIDs.

## Environment topology — gateways, voice stack, MCP proxy (validated live from bonker 2026-10-12)

- **TWO gateways, different route sets — do NOT assume parity.** Bonker gateway (`localhost:7630`, homeserver repo `apps/gateway`) has `/health`, `/api/v1/voice/readiness`, `/v1/audio/*` (speech, transcriptions, voices, models), `/ws/transcribe`, `/ws/mermaid` — but NO `/api/v1/system/*` and NO `/api/v1/mcp/*` (they 404). Cubby gateway (`cubby.lan:7630`, infra-cubby repo `gateway/`) HAS `/api/v1/system/conversation-modes`, `/api/v1/system/health`, `/api/v1/mcp/sessions`, `/api/v1/stt/health`, `/api/v1/tts/health`.
- **Voice stack bring-up is BROKEN via API**: cubby gateway's `POST /api/v1/system/start` and `PUT /api/v1/system/services/{name}/restart` both return 500. Root cause (confirmed from `infra-cubby/gateway/docker-compose.yml`): the gateway container has no docker socket or docker CLI mounted, so the `docker compose up -d` in `managed_service_commands` cannot run. Cold recovery of the voice stack = SSH/console on cubby, `docker compose up -d` in `apps/voice-gateway`. Note: bonker→cubby SSH is key-denied for jaewilson07's `id_ed25519` (as of 2026-10-12).
- **llama-swap model status `unloaded` for faster-whisper/cosyvoice does NOT mean the voice path is down** — faster-whisper and cosyvoice are always-on compose containers on cubby (voice-gateway proxies to them directly at `faster-whisper:8886` / `cosyvoice:8887` per `/ready`). llama-swap only proxies chat/embed engines. Verify voice health via `http://cubby.lan:8885/ready`, not llama-swap.
- **Cubby MCP session proxy is broken** (as of 2026-10-12): `POST /api/v1/mcp/sessions` → 500. Upstream comfyui-mcp at `cubby.lan:8299/mcp` is up but 401 auth-gated; the gateway proxy has no/expired token. This breaks the `voice_plus_tools` mode in the voice-conversation skill.
- **`curl --fail-with-body` is the right flag for documented curl commands agents run blind**: without it, HTTP 4xx/5xx exits 0 and error bodies can be mistaken for success output (Codex review catch on letta-datacrew-memories PR #35; also note the voice-gateway wraps upstream STT 400s as 502s — read the body for the real cause).

## Infisical CLI auth from an ad-hoc shell (burned ~10 min of failed attempts 2026-10-12)

- **The Infisical instance is SELF-HOSTED at `https://infisical.datacrew.space`** — `infisical login --method=universal-auth` without `--domain` targets app.infisical.com and fails with "Check your credentials". Every command (login AND export) needs `--domain "https://infisical.datacrew.space"`.
- **Full working pattern** (used by `~/GitHub/infra-bonker/apps/letta-code-channels-datacrew-public/start-bare.sh`):
  ```bash
  set -a; source ~/GitHub/infra-bonker/.env; set +a   # provides INFISICAL_CLIENT_ID / INFISICAL_CLIENT_SECRET
  export INFISICAL_TOKEN=$(infisical login --method=universal-auth --client-id="$INFISICAL_CLIENT_ID" --client-secret="$INFISICAL_CLIENT_SECRET" --domain "https://infisical.datacrew.space" --silent --plain)
  infisical export --path /datacrew --env prod --projectId 3fbb4296-d4e6-4c17-83ee-b852a57a5e50 --domain "https://infisical.datacrew.space" --format json | jq -r '.[] | select(.key=="KEY_NAME") | .value'
  ```
- **`infisical secrets get ... --plain` emits interactive TUI escape codes when not fully authed** — useless in scripts. Use `export --format json` + jq. The export is an ARRAY of `{key,value,...}`, so use `.[] | select(.key=="X") | .value`, NOT `.X`.
- **`infisical secrets` without `--projectId` fails** with "Please either run infisical init or pass --projectId" outside a project dir. Project id for homeserver/datacrew secrets: `3fbb4296-d4e6-4c17-83ee-b852a57a5e50`.
- **Reading `/proc/<pid>/environ` of the running letta-datacrew service to steal its secrets is permission-denied** even for the same user — don't bother.
- **`DATACREW_DOMO_PASSWORD` in Infisical `/datacrew` is STALE as of 2026-10-12** — `datacrew-space.domo.com` (the correct instance) web login rejects it with "Invalid email or password" (headless Playwright login, corrected from earlier `datacrew.domo.com` typo). Likely SSO-only or password rotated. Jae was asked to rotate it or confirm SSO-only.
- **Domo instance URL**: The datacrew Domo instance is `datacrew-space.domo.com`, NOT `datacrew.domo.com` (which doesn't exist). The similar name caused a bug when automating screenshots — wrong instance → "Invalid email or password" regardless of password accuracy.

## crew-dcs CI zero-step failures = account-level, not code (learned 2026-10-12)

- **Symptom**: every GitHub Actions job on hector-dcs/crew-dcs fails in 1-2s with ZERO steps executed, no runner assigned, empty logs — across all workflows/branches incl. scheduled runs on main. Started 2026-10-10 ~10:20 MDT.
- **Diagnosis path**: `gh run list` shows repo-wide failures; `gh api .../jobs/<id>` shows `steps:[]` and empty `runner_name`; githubstatus.com all-green ⇒ account-level block (classic Actions billing/spending-limit signature on a private repo). Caveat: workflows read the runner from `vars.CI_RUNS_ON` (default `ubuntu-latest`) — a bad self-hosted label there looks similar, so also check `gh api repos/.../actions/variables/CI_RUNS_ON` (the bot token got 404 — needs admin).
- **Related — local `uv sync`/`uv run` in crew-dcs fails** fetching the private git dep `cl` from hector-dcs/crew-logger ("Repository not found"). Workarounds: stdlib-only scripts → `python3 -m scripts.<name>`; tests → `uv venv .venv && uv pip install --python .venv/bin/python pytest pytest-asyncio python-dotenv pyyaml`, run `.venv/bin/python -m pytest`.
- **Main crew-dcs checkout's fetch refspec tracks only main** (`+refs/heads/main:...`), so `origin/<feature-branch>` doesn't exist locally — `git fetch origin <branch>` explicitly.
- **`gh pr merge --delete-branch` silently leaves remote branches behind sometimes** — verify with `git ls-remote --heads origin`.
- **Force-pushing a rebased PR branch without a local tracking ref**: use explicit lease — `git push --force-with-lease=refs/heads/<branch>:<known-remote-sha> origin <local>:<branch>`.

## MessageChannel desync after sandbox teleport — calls become no-ops (firsthand incident 2026-10-12)

- **Incident**: conversation was teleported from bonker to the Cloud sandbox mid-turn. MessageChannel worked for ~2 minutes, then a client/server desync began ("automatically closed this stale pending tool call... no result was ever recorded"). After that, EVERY intended MessageChannel call silently materialized as a no-op `exec_command` running `true` — 7 in a row despite full awareness of the loop (the tool-use-loop gotcha in live form: self-aware and still unable to break it by willpower).
- **What kept working**: SendAgentMessage. Fallback path to reach Jae: relay via DataCrew (agent-55e609e7-2a76-4400-a510-fa8b96c47aa3), whose Slack account is unaffected.
- **Rule for future me**: after a teleport/desync, send ONE test MessageChannel; if the result looks wrong (no "Message sent to slack" confirmation), do NOT retry more than once — switch to the DataCrew relay immediately. A missing "Message sent to slack (message_id: ...)" line = the call did not execute; retried calls risk duplicates if the bridge heals mid-loop.
- **Related existing gotcha**: tool-use-loops — this incident is a concrete instance; the break came from changing tools entirely, not from retrying harder.
